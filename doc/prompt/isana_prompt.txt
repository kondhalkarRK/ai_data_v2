TASK 3 — CREATE: core/conversation_state.py
════════════════════════════════════════════════════════════════

Create a ConversationState manager that:

1. Stores state in st.session_state under 
   key "conversation_state"

2. State structure:
   {
     "active_intent": str | None,
     "last_resolved": {
       "metric": str | None,
       "dimensions": list[str],
       "filters": dict,
       "time_grain": str | None,
       "sql": str | None
     },
     "prior_metric": str | None,
     "prior_dimensions": list[str],
     "prior_filters": dict,
     "prior_time_grain": str | None,
     "turn_count": int,
     "last_question": str | None,
     "is_followup": bool,
     "inherited_context": dict
   }

3. Implements these functions:
   - get_state() → current state dict
   - update_state(intent, resolved, question) 
       → updates after successful query
   - detect_followup(question: str) → bool
       checks for tokens: same, now, also, but,
       only, filter, show, and, too, instead,
       additionally, what about, how about
   - inherit_context(question: str) → dict

   - clear_state() → resets to empty
   - to_context_string() → str
       formats state for LLM prompt injection
   - get_badge_info() → dict
       returns display badge for UI

4. Follow-up detection rules (from ISANA):
   - Short question (≤ 7 words) + trigger token
     → is follow-up
   - "same but for X" → inherit all, change X
   - "now show by Y" → inherit metric+filters, 
       change dimension to Y
   - "only for Z" → inherit all, add filter Z
   - "what about W" → inherit metric, 
       change dimension/filter to W

TASK 4 — CREATE: core/semantic_resolver.py
════════════════════════════════════════════════════════════════

Create a semantic resolver adapted from ISANA's 
semantic_resolver.py for DataFrame (CSV) domain.

Function: resolve_semantics(validated: dict, df: pd.DataFrame) → dict

Input validated dict contains:
{
  "intent_type": str,
  "metric": str | None,
  "dimensions": list[str],
  "filters": list[dict],
  "time_grain": str | None,
  "limit": int | None,
  "order_by": list[dict]
}

Steps to implement:

STEP 1 — Intent bypass routing:
  - If intent_type in 
    ["unsupported", "scenario_analysis", 
     "objective_override"]:
    return pass-through contract with 
    expression="1", bypass=True

STEP 2 — Metric resolution:
  - Try metric_registry.resolve_metric(metric)
  - If not found, try synonym lookup:
    metric_registry.find_metric_by_synonym(metric)
  - If still not found, try 
    semantic phrase mapping from 
    semantic_loader synonyms
  - If found: use registry expression
  - If not found: fall back to 
    intent expression (LLM-provided)
  - Track resolution source:
    "registry" | "synonym" | "llm_fallback"

STEP 3 — Dimension normalisation:
  Alias map:
    "regions" → "region"
    "categories" → "category"  
    "colours" → "colour_name"
    "colors" → "colour_name"
    "salespeople" → "salesperson"
    "reps" → "salesperson"
    "models" → "model"
    "makes" → "make"
    "brands" → "make"
  
  Also validate each dimension column 
  exists in df.columns

STEP 4 — Filter validation:
  - Validate each filter column 
    exists in df.columns
  - Normalise date filters:
    year as integer
    month as integer (1-12)
    support month names → integers

STEP 5 — Smart defaults:
  - If no time filter and date column exists
    in df: add advisory warning 
    (do NOT auto-apply filter for CSV,
     data may be single-period)
  - If metric has default_filters in registry:
    apply them

STEP 6 — Build execution contract:
  Return dict:
  {
    "expression": str,
    "display_label": str,
    "format": str,
    "dimensions": list[str],
    "filters": dict,
    "time_grain": str | None,
    "limit": int | None,
    "order": str,
    "metric_name": str | None,
    "resolution_source": str,
    "bypass": bool,
    "warnings": list[str]
  }

════════════════════════════════════════════════════════════════
INTEGRATION WIRING — HOW ALL PIECES CONNECT
════════════════════════════════════════════════════════════════

The complete flow after integration:

1. User types question in tab_query.py

2. tab_query.py calls run_query(working_df, question)

3. nlq_engine.run_query():
   a. Load conv_state = get_state()
   b. detect_oob(question) 
      → if True: return OOB evidence immediately
   c. detect_followup(question)
      → if True: inherit_context() from conv_state
   d. Normalise + fingerprint question
   e. Check session cache (Layer 1)
   f. Check disk cache (Layer 2)
   g. Call intent_resolver.resolve_intent(
        question, df, status, conv_state
      )
   h. Call semantic_resolver.resolve_semantics(
        intent, df
      ) → execution_contract
   i. If not bypass:
        sql_compiler.compile_from_contract(
          execution_contract
        )
      Else: fallback to nlq_to_sql()
   j. run_sql(sql, df)
   k. build_evidence(sql, result, path, question)
   l. update_state(intent, resolved, question)
   m. Cache both layers
   n. Return (result, sql, None, evidence)

4. tab_query.py receives 4-tuple:
   - Renders result table
   - Shows execution badge
   - Shows conversation context banner
   - Shows evidence detail expander
   - Shows metric resolution info
