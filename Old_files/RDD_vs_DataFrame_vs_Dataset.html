RDD vs DataFrame vs Dataset

Three ways Spark represents distributed data. They differ in how much Spark knows about your data, and that decides how much Spark can optimise for you.

RDD

Resilient Distributed Dataset, Spark 1.0

A distributed list of objects. Spark does not know what is inside, so it runs your lambdas exactly as written.

Maximum control, minimum help.

DataFrame

Named columns, Spark 1.3

A distributed table with a schema. Spark sees columns and types, so Catalyst and Tungsten can optimise the work.

The default choice, and the only structured API in PySpark.

Dataset

Typed objects, Spark 1.6

A DataFrame whose rows are typed objects, such as Employee. Same optimizer, plus compile-time type checks.

Scala and Java only.

How they relate

They are not three separate engines. DataFrames and Datasets are built on RDDs, and since Spark 2.0 a DataFrame is just a Dataset of generic Row objects.

DataFrameDataset[Row], Python, Scala, Java, R
Dataset[T]typed, Scala and Java only
Catalyst optimizer + Tungsten executionquery planning, code generation, binary row format
RDDthe base layer everything finally runs as

How the API grew

  1. May 2014Spark 1.0

    RDD is the only API.

  2. March 2015Spark 1.3

    DataFrame adds schemas and Catalyst.

  3. January 2016Spark 1.6

    Dataset adds type safety in Scala and Java.

  4. July 2016Spark 2.0

    APIs unified: DataFrame = Dataset[Row].

The same task, three ways

Task: keep employees earning more than 50000 and add up their salary per state. The two Python examples were run on a local Spark session and the output shown is real. The Scala example is for reference.

RDD (PySpark)

Lambdas on tuples, indexes like x[2].

python
data = [(1001, "John Smith", 50000, "CA"),
        (1002, "Maria Garcia", 72000, "NY"),
        (1003, "Ravi Patel", 65000, "TX"),
        (1004, "Emily Chen", 48000, "CA")]

sc = spark.sparkContext
rdd = sc.parallelize(data)

# x is a plain tuple: Spark does not know what x[2] means
result = (rdd.filter(lambda x: x[2] > 50000)
             .map(lambda x: (x[3], x[2]))
             .reduceByKey(lambda a, b: a + b))

print(result.collect())

Output

[('NY', 72000), ('TX', 65000)]

DataFrame (PySpark)

Named columns and built-in functions.

python
from pyspark.sql.functions import col

cols = ["employee_id", "employee_name", "salary", "state"]
df = spark.createDataFrame(data, cols)

# Spark knows "salary" and "state" are columns, so it can optimise the plan
result = (df.filter(col("salary") > 50000)
            .groupBy("state")
            .sum("salary"))

result.show()

Output

+-----+-----------+
|state|sum(salary)|
+-----+-----------+
|   NY|      72000|
|   TX|      65000|
+-----+-----------+

Dataset (Scala)

Typed objects, fields checked by the compiler.

scala
// Scala only
case class Emp(employee_id: Int, employee_name: String, salary: Int, state: String)
import spark.implicits._

val ds = spark.read.option("header", "true").option("inferSchema", "true")
              .csv("/FileStore/tables/OfficeDataProject-13.csv")
              .as[Emp]                      // DataFrame -> typed Dataset

val result = ds.filter(e => e.salary > 50000)      // typed lambda
               .groupByKey(e => e.state)
               .mapGroups((state, rows) => (state, rows.map(_.salary).sum))
result.show()

// ds.filter(e => e.salry > 50000)          // does NOT compile: salry is not a field of Emp

All three give the same answer. The DataFrame version is shortest and lets Spark optimise it; the RDD version says how to compute, while the DataFrame version says what you want.

Why DataFrame and Dataset are faster

Because Spark knows the schema, every query goes through the Catalyst optimizer before it runs. An RDD lambda is a black box, so none of this can happen.

  1. Analysis. Column names and types are resolved against the schema.
  2. Logical optimization. Filters are pushed down, unused columns are dropped, constants are folded.
  3. Physical planning. Spark picks the cheapest strategy, for example which join to use.
  4. Code generation. Tungsten generates compact Java code that works on its binary row format.

Real result.explain(True) output for the DataFrame example, trimmed to the interesting part. The optimizer rewrote the plan by itself:

Analyzed plan (what you wrote)

Aggregate [state], [state, sum(salary) AS sum(salary)]
+- Filter (salary > cast(50000 as bigint))
   +- LogicalRDD [employee_id, employee_name, salary, state]

Optimized plan (what Spark will run)

Aggregate [state], [state, sum(salary) AS sum(salary)]
+- Project [salary, state]                                   <- unused columns dropped
   +- Filter (isnotnull(salary) AND (salary > 50000))        <- cast removed, null check added
      +- LogicalRDD [employee_id, employee_name, salary, state]

Typed Dataset caveat. A Dataset lambda such as e => e.salary > 50000 is also opaque to Catalyst, and Spark has to rebuild each object to call it. Column expressions such as col("salary") > 50000 stay fully optimisable. PySpark caveat. DataFrame code runs in the JVM, but Python UDFs and df.rdd.map(lambda ...) move rows to Python and back, which is slow.

Converting between them

PySpark

python
# RDD -> DataFrame
df2 = rdd.toDF(["employee_id", "employee_name", "salary", "state"])
# or: df2 = spark.createDataFrame(rdd, schema)

# DataFrame -> RDD (each item becomes a Row object)
rdd2 = df.rdd
print(rdd2.take(1))
print(df.rdd.map(lambda row: row.salary).collect())

Output

[Row(employee_id=1001, employee_name='John Smith', salary=50000, state='CA')]
[50000, 72000, 65000, 48000]

Scala

scala
// Scala
val ds = df.as[Emp]        // DataFrame -> Dataset
val df3 = ds.toDF()        // Dataset   -> DataFrame
val rdd3 = ds.rdd          // Dataset   -> RDD

Converting a DataFrame to an RDD and back throws away the schema information the optimizer needs, so do it only when you must.

Which one should you use?

  1. Writing PySpark (as in your Databricks notebooks)? Use DataFrames.
  2. Writing Scala or Java and want compile-time safety on domain objects? Use Datasets.
  3. Data cannot be given a schema, or you need low-level control? Use RDDs.
RDD
  • Unstructured text, logs, binary data
  • Custom partitioners and mapPartitions tuning
  • Maintaining old Spark 1.x code
DataFrame
  • ETL, reading CSV, JSON, Parquet and Delta
  • Joins, aggregations, window functions, SQL
  • Almost everything you do in Python
Dataset
  • Scala or Java applications with case classes or beans
  • When a field typo must fail at compile time, not in production

Databricks note: some compute types, such as serverless, do not support the RDD API or sparkContext. Another reason to prefer DataFrames.

Interview questions

Is a DataFrame faster than an RDD? Why?

Usually yes. A DataFrame has a schema, so the Catalyst optimizer can reorder and prune the plan, and Tungsten stores rows in a compact binary form. An RDD lambda is a black box that Spark can only run as written.

Is the Dataset API available in PySpark?

No. Dataset (the typed API) exists only in Scala and Java. In PySpark, DataFrame is the structured API, and it runs on the same engine.

What does 'DataFrame is Dataset[Row]' mean?

Since Spark 2.0 a DataFrame is simply a Dataset whose items are generic Row objects. A Dataset[Employee] has the same engine and optimizer but gives you real Employee objects with compile-time checks.

Is a DataFrame built on top of an RDD?

Yes. Every DataFrame executes as RDDs underneath, which is why df.rdd works and why lineage-based fault tolerance is the same for all three.

When do you still need RDDs?

For unstructured data, custom partitioners, low-level control with mapPartitions, or old code. For tables, joins, aggregations and Delta, use DataFrames.

Does PySpark DataFrame code run in Python?

The plan runs in the JVM. Python only builds the plan. It slows down when you add Python UDFs or call .rdd.map(lambda ...), because rows then travel between the JVM and Python.
