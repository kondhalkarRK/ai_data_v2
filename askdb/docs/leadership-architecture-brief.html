Ask DB: Leadership & Architecture Brief

How AI Chat, the Semantic Layer, the Entity Catalog, the Knowledge Graph and SQL generation actually work in this PoC.

Written from the current codebase (October 2026), not from a target architecture. Where the system has a gap, this brief says so.

The one-sentence story Ask DB answers business questions from governed business definitions first, and only brings in the AI model when a question needs reasoning. Every AI-written query must pass the same validation as our own, and the AI never sees customer data rows.

1. AI Chat end-to-end flow

This is the real sequence the chat service runs for every question. Steps 3–8 run in our own code, with no AI call and no database write. The benchmark replays exactly these steps offline.

When you ask a question, we first translate it into our own business language: which metric, which brand, which period. We then build the query from definitions the business has approved. The AI model only gets involved when the question needs real reasoning, and even then it must pass the same checks. If we aren't confident, we ask you rather than guess.

2. Schema-based vs LLM-based questions

2.1 Where the schema/semantic rules are stored

Both in YAML and in code, by design. The YAML holds what the business means. The code holds how a question shape becomes SQL and how SQL is checked.

File (per domain: automotive, insurance)What it controls
semantic/packs/<domain>/semantic_model.yamlTables and columns (the allowed-schema whitelist), relationships/joins, measures (e.g. Revenue = SUM(total_sales)), dimensions, hierarchies, value domains (which columns hold business values and their synonyms, e.g. “saloon” → Sedan), business entities, ALWAYS/NEVER domain rules.
semantic/packs/<domain>/business_glossary.yamlBusiness terms, definitions, synonyms, SQL expression, disambiguation (“Top selling means units unless revenue is named”), example questions, domain rules.
semantic/packs/<domain>/chat_vocabulary.yamlThings the data can't answer and what to suggest instead (profit, margin, CNG, satisfaction), model names that are also everyday words (“City”, “Venue”), words that are never entity names.
semantic/packs/<domain>/entity_catalog.yamlBusiness grouping of value domains, extra columns to watch, schemas monitored for drift.
services/chat/question_understanding.pyIntent, metric, dimension, period and analysis detection from the question text.
services/chat/templates.py, semantic_analytics.pyThe governed SQL builders: breakdowns, rankings, market share, comparisons, top-N per group, growth, running totals, moving averages, year-window comparisons. Joins come from the pack relationships.
services/chat/time_periods.pyBusiness periods (“last 3 months”, “YTD”, fiscal year), anchored to the latest date in the data, not the calendar.
services/chat/semantic_context.py, analytics/sql_guardrails.pyThe validator (SQL must match the plan and the semantic pack) and the safety guardrails (read-only).
services/chat/decision_engine.pyConfidence scoring and the semantic-vs-AI routing decision.

2.2 How the application decides a question needs no LLM

  1. A metric was identified (revenue, units, premium, loss ratio…).
  2. Every named value was matched to real data (brand, state, segment…).
  3. The question shape is one our governed compiler supports, and the compiled SQL passes plan validation.
  4. The shape is “simple”: one business dimension and no window logic. Complex shapes go to the AI by policy (see 2.4).

2.3 Verified examples: answered without the LLM

2.5 What happens if the LLM is unavailable

  • Simple questions are unaffected. The semantic layer, narration, charts and insights need no AI.
  • Complex questions fall back to governed SQL where it exists.
  • Circuit breaker: after 3 consecutive AI failures the system stops calling the provider for 45 seconds and fails fast. An optional fallback model can be configured.
  • If there is no governed SQL and no AI, the user sees a friendly explanation with suggested questions, never a technical error.

3. Leadership question: why not use the LLM for everything?

Schema-first gives us

  • Accuracy: “Revenue” is always SUM(total_sales), the way Finance defines it.
  • Speed: no model round-trip for most questions.
  • Governance: definitions are version-controlled YAML, reviewed like code.
  • Consistency: the same question gives the same SQL and the same number for every user, every day.
  • Cost: zero tokens for the majority of questions.

The LLM gives us

  • Flexibility: understands unusual phrasing.
  • Reasoning: window logic, multi-period comparisons.
  • Complex analytics beyond the governed set.
  • Follow-ups: uses the prior query as context.
  • Ambiguity handling: restates unclear questions into governed terms.

Why hybrid wins

  • An LLM alone can write SQL that runs but answers the wrong question, for example ranking “top selling” by revenue or confusing dealer with salesperson.
  • Our semantic layer gives the AI the rules, and our validator checks that it followed them.
  • If the AI is down, too slow or too costly, the business keeps getting answers.
An LLM on its own is like a brilliant new analyst on day one: fluent, fast, and unaware of how we define revenue. Our semantic layer is the company rulebook. For everyday questions we answer straight from the rulebook: instant, free and consistent. For harder questions the analyst does the reasoning, but every query is checked against the rulebook before anyone sees a number.

4. Is schema-generated SQL always correct?

It is consistent and governed, and correct to the extent the definitions are correct. These are the checks behind it:

ControlWhat it guarantees
Business glossaryEach business word maps to one approved formula, with disambiguation rules (“top selling” = units, not revenue).
Semantic definitionsMeasures, dimensions and hierarchies are declared once, in the semantic pack, per domain.
Allowed joinsJoins come from declared relationships (e.g. sales → dealer on dealer_id); the AI is given only the relevant ones.
Allowed schemaAny table or column not in the active pack is rejected. Insurance tables can't leak into automotive answers.
Mandatory filtersEvery named brand, city, segment or state must appear in the SQL, or it is rejected.
Shape validationRankings sort the right way; top-N per group partitions correctly; growth uses LAG; requested years and periods are present.
Safety guardrailsSELECT only; no writes, no chained statements, no file/sleep functions; read-only transaction; timeout; row limit.
Dry run (EXPLAIN)The database checks the query before it runs.
Confidence gateLow confidence → clarification, not a number.
Release benchmark437 questions across both domains; release gate is 95% per domain. First unseen run: 95.9% (automotive 95.5%, insurance 96.2%); misses were then fixed generically to 100%.
Limitations to state openly
  • The validator checks structure (tables, filters, sort order, windows), not every possible meaning. A query can pass and still answer a slightly different question. Example found while preparing this brief: “Top SUV models in Maharashtra” or “Top sedan models by revenue” is grouped by body style (segment) instead of by model. Brand and state filters work correctly (“Top Tata models”, “Top models in Maharashtra”). That is a planner gap we can fix.
  • The benchmark grades SQL against expectations; it does not execute against live data. The 100% figure is after fixes, so it is no longer an unseen score.
  • The governed compiler covers a bounded set of analysis shapes. Anything outside it relies on the AI plus validation, or a clarification.
  • Correctness depends on the definitions. If a glossary formula is wrong, it is consistently wrong. That is why business ownership of the glossary matters.

5. Dynamic data growth

5.1 The Entity Catalog

The Entity Catalog is the metadata layer that keeps AI Chat aware of what is actually in the warehouse. It records every business value (brand, model, city, state, segment, fuel type, colour, insurance product, channel…), how often it occurs, when it first appeared, and any schema change.

TriggerWhen it refreshes
StartupEvery time the API starts.
Data loadA data pipeline can call the refresh endpoint with trigger = data_load when a load finishes.
ManualAn admin presses Refresh in the Admin Center.
Unknown name in a questionA targeted lookup for just that word (with a 10-minute cooldown per word), then the question is re-planned.

After a refresh, the live value dictionary is swapped and the semantic, graph and answer caches are cleared, with no restart. Refreshes never run on every query.

5.2 What happens when a new value arrives

New…Does AI Chat pick it up automatically?
Brand / make, model, city, state, segment, fuel type, colourYes These are value domains: picked up on the next refresh, or immediately via the unknown-name lookup. Marked “new” for 7 days, with a readiness status (AI-ready, missing synonyms, low confidence, needs review).
Insurance product line, coverage type, channel, region, stateYes Same mechanism.
Dealer (by name), salesperson (by name)Partly New dealers appear in “top dealers” and every ranking immediately, because rankings read the data. Filtering by a named dealer isn't in the AI value dictionary yet; those columns are watched only.
A synonym business users invent (“sub-4m SUV”)Needs review Added once to value_aliases in the semantic model; the catalog flags values with missing synonyms.
New column / removed column / type changeDetected, not auto-applied Schema drift is recorded with an impact rating (e.g. removed column = High impact on AI Chat). A person approves semantic-layer changes. That's deliberate governance.
New metric (e.g. “discount %”)Manual Needs a glossary/semantic-model entry, and today also a small code change (see Risks).
New brands, cities, models and products are picked up automatically. The catalog sees them on the next refresh, or the moment someone asks about one. New metrics and structural changes are flagged for a person to approve, because we don't want the AI to quietly redefine what “revenue” means.

6. Knowledge Graph usage today

Direct answer The Knowledge Graph is not in the AI Chat runtime path today. It is a visual, explorable representation of the same semantic model that AI Chat uses. Chat reads the semantic YAML directly; it does not query the graph.

6.1 What the Knowledge Graph is, concretely

  • Built by SemanticService from semantic_model.yaml and business_glossary.yaml: tables become actors, events and entities; measures become outcomes; relationships become edges. Cached; rebuilt from the Admin Center or after a catalog refresh.
  • Served at /api/v1/semantic/{industry}/ontology and shown on the Knowledge Graph page (galaxy view, roles, filters, relationship labels).
  • It does not read value domains, so individual brands and cities are not graph nodes.

6.2 Does a question route through the graph?

Today the Knowledge Graph is the visual map of our business model: the same definitions AI Chat uses, drawn so business and data teams can see and review how concepts connect. AI Chat uses those definitions directly, not by walking the graph. Making the graph an active part of reasoning is the next phase.

Why it isn't in the runtime path yet: the two current domains have a single fact table each with a few dimensions (a star schema). Joins are one hop, so a graph traversal adds no accuracy today. The graph earns its place when there are many domains, multi-hop relationships, or questions across domains.

7. Future vision: why we need a Knowledge Graph

Cross-domain analytics

“Do regions with higher car sales have higher motor-insurance claims?” The graph knows Region links Sales and Claims and plans the join safely.

Business relationship discovery

Show leaders how dealers, regions, models and targets connect, and which metrics depend on which data.

Impact analysis

“If the dealer table changes, which KPIs, dashboards and AI answers are affected?” This is already partly visible in schema-drift impact ratings.

Entity resolution with context

“Punch in Pune”: the graph knows Punch is a Tata model and Pune is in Maharashtra, so it resolves names through their relationships.

Semantic search

Find any concept, metric, document or dataset by business meaning, not table names.

Context-aware AI and recommendations

Suggest the next best question (“You looked at SUV revenue; dealer performance for SUVs is related”) and give the AI a precise, small context instead of the whole schema.

As we add domains, the hard part stops being “write SQL” and becomes “know how our business connects”. The Knowledge Graph is that memory. It lets the AI answer questions across sales, insurance and finance safely, explain why a number moved, and tell us what breaks when data changes.

8. Risks and gaps: an honest assessment

Current strengths

  • Governed-first architecture: most questions need no AI, every answer path is validated, and the AI never sees result rows.
  • Works without an AI model; degrades gracefully when the provider is down (circuit breaker, governed fallback).
  • Clarify-instead-of-guess, with clickable options; answers carry confidence and “data as of”.
  • Live entity awareness: new values are found on refresh or on demand; schema drift is detected with impact ratings.
  • Model-agnostic: OpenAI, Claude, Gemini, Azure OpenAI and local Ollama models from one catalog; per-user quotas and cost tracking.
  • Measured: a 437-question benchmark with a 95% release gate per domain; 370+ automated API tests.
  • Executive narration without AI cost: summary, highlights, insight, focus area.

Current weaknesses and architectural gaps

Knowledge Graph not used at runtimeLeadership may assume it powers the AI.Position it accurately (section 6); next phase: graph-driven join planning and cross-domain questions.
Some business logic duplicated in code (metric formulas, join maps, intent words) as well as YAMLAdding a metric needs YAML + code; risk of the two drifting.Generate formulas and joins from the semantic pack only.

Demo risks

  • Stale data lowers the Data Trust score (freshness). Run the daily top-up script before the demo and press “Run checks”.
  • AI provider latency or quota: stick to simple questions if the network is slow; they need no AI.
  • Weekly quota: admins have 100 AI calls / 60k tokens per week. Check the Admin Center before rehearsing.
  • Avoid “Top SUV/sedan models…”, “why…”, and “unusual patterns” until those gaps are fixed. Safe alternatives that were verified: “Top models in Maharashtra”, “Top Tata models by units”, “SUV sales by state”, “Compare Tata vs Mahindra revenue”.
  • Cached answers return instantly for 5 minutes. Don't present that speed as typical.

Where leadership may challenge

  • “Is the Knowledge Graph real or decoration?” Answer with section 6: it is the shared model made visible, and runtime use is the roadmap.
  • “100% accuracy?” Say 95.9% unseen; 100% after fixes; SQL graded, not executed.
  • “Who owns the definitions?” Today the data team, in version-controlled YAML. Propose business stewardship.
  • “How does it scale to 20 domains?” One semantic pack per domain; the remaining code-level duplication must go first.

9. Leadership Q&A preparation

Recommended answers, each backed by current behaviour. The small grey line under each answer points to the evidence.

1. Why not use ChatGPT directly against the database?

Because it doesn't know our definitions. It can write SQL that runs but measures the wrong thing, such as ranking “top selling” by revenue, confusing dealer with salesperson, or ignoring a fiscal year. We answer most questions from approved definitions with no AI, and every AI-written query is validated against those definitions before it runs. The AI also never sees our data rows, only table names and matched values.

Evidence: semantic layer + validator (semantic_context.py); narration is deterministic (narration.py).

2. How do you prevent hallucinated SQL?

Four layers. The AI is given the plan as hard requirements. Its SQL must use only tables and columns in the semantic pack, include every named filter, and follow the right ranking, window and period logic. It must pass read-only safety rules and a database dry run. If it fails, it gets one correction attempt, and then we fall back to our governed query or ask the user.

Evidence: llm_assist.generate_validated_sql, validate_sql_against_plan, sql_guardrails.py.

3. How do you ensure metric consistency across users?

Each metric is defined once in the business glossary. Simple questions compile to the same SQL for everyone, every time. AI-written SQL must use the same formulas. Results are cached briefly and invalidated when the data changes.

Evidence: business_glossary.yaml, query_cache.py.

4. What is the role of the Semantic Layer?

It is the translation layer between business language and data: which words mean which metrics, which values exist, how tables join, and what is never allowed. It powers SQL generation, validation, AI prompts, the Knowledge Graph and the Entity Catalog from one source.

Evidence: semantic/packs/<domain>/*.yaml.

5. What business problem does the Knowledge Graph solve?

Today it makes our business model visible and reviewable: how dealers, vehicles, sales, regions and outcomes connect, and which metrics come from where. Next, it becomes the engine for cross-domain questions, impact analysis and context-aware recommendations. We are deliberately honest that it is not yet in the AI answer path.

Evidence: SemanticService._compile_snapshot; chat does not call the graph.

6. How do you handle new entities and new business terms?

New values such as brands, models, cities and products are discovered automatically by the Entity Catalog on startup, after a data load, on demand, or the moment a user asks about an unknown name. New business terms and synonyms are added once to the glossary and reviewed like code. Schema changes are flagged with an impact rating for approval.

Evidence: catalog/service.py (triggers), catalog/drift.py.

7. How do you measure AI accuracy?

With a 437-question release benchmark across automotive and insurance, including spelling mistakes, aliases, complex analytics and multi-turn follow-ups. The release gate is 95% per domain. The first unseen run scored 95.9%. Each answer also carries a confidence score, and low confidence becomes a clarification.

Evidence: docs/nlq-benchmark-report.md, tests/test_nlq_benchmark.py.

8. How do you control AI cost?

Most questions use zero tokens. Narration uses zero tokens. AI prompts are compact (only the relevant schema, capped in size). Each user has a weekly quota (users: 50 calls / 60k tokens; admins: 100 / 60k). The Admin Center shows cost per question, questions per dollar, spend against the monthly budget, and per-user consumption. Complex questions can also be switched to governed-only.

Evidence: governance/quota.py, usage.py, Admin Center → LLM Cost & Usage Intelligence.

9. What happens if the LLM is unavailable?

The business keeps getting answers. Simple questions, narration, charts and dashboards don't need the AI. Complex questions use our governed SQL. A circuit breaker stops calling a failing provider, and a fallback model can be configured. Users see a friendly message, never a technical error.

Evidence: services/llm.py (circuit breaker), decision_engine.decide_route.

10. How is this different from ThoughtSpot, Power BI Copilot or Fabric Copilot?

Those are mature platforms, best inside their own ecosystems. Ask DB is a governed layer we own. Business definitions live in our version control, it is model-agnostic (cloud or local models), it works with no AI model at all, it encodes domain rules specific to Indian automotive and insurance, and it shows confidence, clarifications and executive narration by design. The PoC proves the governed-first pattern; build-versus-buy is a separate decision we can inform with these results.

Positioning answer; avoid detailed claims about competitor internals.

11. How do you audit AI-generated answers?

Every question stores the SQL that ran, whether it came from the semantic layer or the AI, the confidence and trust breakdown, row count, timings, and AI tokens and model. Admins can review usage per user and per execution mode. Users don't see execution internals; admins do.

Evidence: query_history, llm_usage tables. Gap: no dedicated immutable audit log yet.

12. How do you govern business definitions?

Definitions are YAML files in source control, so every change has an author, a review and a history. ALWAYS/NEVER rules capture policy (“never confuse salesperson with dealer”). The Semantic Model and Entity Catalog screens let stewards review terms, values, synonyms and readiness. Next step: formal business ownership of each term.

13. How do you scale to multiple domains?

Each domain is a semantic pack (automotive and insurance today) with its own schema whitelist. Queries can't cross domains by accident. Adding a domain means a new pack plus its question shapes. To scale efficiently, we will remove the remaining domain logic in code so a new domain is mostly configuration, and move caches to shared infrastructure for multiple servers.

14. How do you handle ambiguous questions?

We ask instead of guessing. Vague questions (“show me the numbers”), ambiguous ones, unknown names and unsupported metrics (“profit” without cost data) get a clarification with 3–5 clickable interpretations. If an AI model is available, it first tries to restate the question in governed terms, and that restatement is re-checked by our planner.

15. Can users trust the results?

Each answer shows a confidence level, the data “as of” date, and notes on how the question was read (spelling corrections, interpretations). Numbers come from approved definitions and validated SQL. Data Trust monitors freshness, completeness and accuracy separately. Linking that score into each answer is the next improvement.

16. How do you support follow-up questions?

The system remembers the previous question's metric, filters and grain. “What about Maharashtra only?” or “Show bottom 5 instead” changes just that part. A question that names its own metric and scope starts fresh, so context doesn't leak.

Evidence: conversation_context.py, semantic_query_planner.is_self_contained.

17. Why did you choose a hybrid architecture?

To get the accuracy, speed, cost and governance of approved definitions for the 80% of everyday questions, and the reasoning of AI for the rest, always under the same validation. It also removes dependency on any single AI vendor.

18. How does the Entity Catalog improve AI understanding?

It gives the system a live list of what actually exists in the data. When someone types “Mahindar XUV in Pune”, it knows Mahindra, XUV and Pune are real values, applies them as mandatory filters, and can tell the user when a name isn't in the data instead of returning an empty or wrong answer. It also flags values that are new, missing synonyms or low-confidence.

19. How does Data Trust integrate with AI Chat?

Honestly: partially. Answers show the data “as of” date, and cached answers are invalidated when data changes. The Data Reliability Center scores freshness, accuracy, completeness and consistency separately, but AI answers don't yet show a warning when their source table has failing checks. That is a defined next step.

Evidence: dataAsOf in answers; dqFailed is not populated yet.

20. What would be the next phase after this PoC?

  1. Wire Data Trust into every answer (trust badge, warnings).
  2. Make the semantic pack the single source of truth: no metric or join logic in code.
  3. Knowledge Graph in the runtime path: graph-based join planning, cross-domain questions, impact analysis.
  4. New governed analyses: anomalies, root-cause (“why did X drop”), forecasting in chat.
  5. Enterprise hardening: SSO, shared cache, immutable audit, monitoring, business stewardship of definitions.
  6. Semantic document search for the Knowledge Hub.

Additional questions worth preparing

Does our data leave the company when the AI is used?

Data rows don't. The AI receives the question, table and column names, approved formulas, and the specific values the user named (e.g. “Tata”). Results, narration and insights are produced locally. Local models (Ollama) are supported if even that must stay in-house.

Who can see and do what?

Users ask questions within their weekly quota. Admins also see the Admin Center: usage, cost, LLM settings, the Entity Catalog, monitoring and execution details. All AI queries are read-only, with time limits and row limits.

How fast is it, and how will it scale?

Simple questions skip the AI entirely, and every stage is timed (understanding, AI, validation, execution) for monitoring. For scale: the analytics database is read-only to the AI path, results are row-limited, and the next step is shared caching and horizontal API servers.

What is the Data Trust score and why might it drop?

It is a weighted score across accuracy, completeness, consistency, timeliness, validity and uniqueness, based on rule pass rates. It drops mostly when data isn't refreshed, because freshness is measured against today. The fix is to load data, not to change the rules.

Can a user break or change the data through chat?

No. Only single SELECT statements are allowed. Writes, chained statements and dangerous functions are blocked, and queries run inside read-only transactions with a timeout.
