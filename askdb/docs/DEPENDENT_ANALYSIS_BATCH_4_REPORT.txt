1. SCOPE AND OUTCOME

This batch extends the existing verification tooling, not the agent architecture.
The current simple-question path, semantic formulas, joins, regional permissions,
SQL guards, report workflow and four-step/two-call dependent limits are retained.
No new model call, execution capability, package, migration or database setup was added.

The previous acceptance runner only inspected flat columns/rows events. Dependent
results are stored in analyticalExecution, so that runner could not validate their
full evidence. It now checks every step and its visible display snapshot.

2. NEW ACCEPTANCE CHECKS

For human-supplied dependent references, the runner checks:
  - Interpreted intent separately from results and response state.
  - Ordered steps/operations and dependencies, without relying on model-chosen IDs.
  - Every approved measure, grouping, exclusion/filter, period and baseline.
  - All result columns/rows, verification state, selected count and total group count.
  - Independent reconciliation states and explicit unanswered parts.
  - Displayed step identity, columns, row count and verification state against execution.
  - Display text against the narrative being reviewed, not a different plausible answer.
  - Exact approved narration separately from numerical correctness.
  - The shared two-call Chat budget; AskBI retains its separate report budget.

Decimal JSON strings are compared with Decimal arithmetic using an absolute tolerance
of 0.000001, without a large relative tolerance. NULL, zero, booleans and text labels
remain distinct; integer outputs must match exactly. Unexpected columns and
missing/extra steps cannot silently pass.
Ordering is exact unless the reviewer explicitly allows unordered rows; duplicate
row multiplicity is preserved. Ties are not collapsed into a set.

Incomplete references, missing narration review and missing usage remain unknown or
incomplete, not automatic successes. A correct intent with wrong results fails.
References carry reviewer/source-SQL hash/revision/holdout declarations; those fields
do not independently prove human authorship, SQL correctness or unseen status.
No reference answers or holdout questions were generated as substitutes for the user.

The offline validate command checks reference contracts before any login/network
operation. Live capture also performs that preflight before prompting for credentials.
Captures retain bounded usage/counters, status, hashes and response IDs, not raw
questions, SQL, result rows, prompts, provider errors, cookies or passwords.

3. USAGE GAP FIXED

Previous usage telemetry identified the first interpretation model but aggregated the
second inventory check. That could hide a different fallback model in a claimed
same-model comparison. The interpreter now records each actual call's model, input
tokens, output tokens, estimation state and completion evidence.

Shared Chat metadata/audit include modelsUsed, modelUsageComplete, initial and
verification input/output token counts. Unknown/timeout usage is not invented as a
completed call. A circuit-open second dispatch is not counted as an actual model call.
If other report calls are outside the tracked interpreter records, usage completeness
is false rather than claiming every report model was recorded by this narrow change.

The paired runner supports typed-baseline/dependent captures in addition to existing
legacy/typed comparisons. It requires matching cases, gold, principal/scope, warehouse
revision, configured model, all observed call models and cache conditions. A fallback
model mismatch or missing per-call evidence makes the pair incomparable. Revision
labels are operator attestations; the reviewer must actually freeze the warehouse.
Performance comparisons require both paired answers to pass correctness review.
No real token savings, accuracy percentage or speedup has been measured in this batch.

4. SECURITY REGRESSIONS

Visible synthetic tests verify:
  - Model-supplied SQL, provider, scope or budget authority is rejected.
  - Excess call budgets, wrong-scope load evidence and empty source revisions fail
    plan review before execution.
  - Hostile text in a selected entity remains data in the CTE relation; it does not
    become SQL or instructions and does not drop the fixture table.
  - Timeout publishes no result rows/SQL and does not trigger an analytical retry.
  - Scope revocation at final publication discards results, SQL and display cards.
  - Follow-up provider payloads exclude prior result summaries and SQL.
  - Model/circuit/timeout/empty-response usage stays distinguishable.
  - Acceptance cannot overlook denied-response data hidden in step metadata.

Existing suites also retain owner-scoped history/ratings, cancellation, current-scope
SQL, read-only mode, row/cohort caps, sparse comparisons and missing-baseline checks.
These are targeted security regressions, not a penetration test or compliance certificate.

5. NATIVE SQL CHECKS PREPARED

The opt-in PostgreSQL fixture now covers all five visible development shapes:
  selected month and reconciled contributing factors;
  selected region then models inside it;
  period comparison ordered by change;
  opposite changes in two measures;
  fixed cohort compared with its own history.

Four added cases compare final values with separately written visible reference SQL.
The original selected-period/reconciliation case remains. These references are
implementation fixtures, not human-reviewed office references or blind holdouts.
The existing empty disposable test-database guard and rollback are unchanged.
No connection to an office, demo or client warehouse was made.
