## User experience

One Ask Analytics composer handles KPI answers, dimensional analysis, tables, daily
trends, reports, dashboard composition and selected-panel refinements. There is no
default panel count. Simple totals return one KPI, simple trends one chart; the LLM
chooses a bounded composition for compound requests (maximum six panels). Unsupported
metrics, ambiguous requests and invalid plans ask for clarification rather than
inventing data. Discount is not presently a supported automotive metric.

Panels offer visualization selection, chart/data view, remove, retry, CSV export,
definitions, actual query evidence, freshness and Data Trust navigation. Existing
heatmap/treemap previews are reused. The field editor uses the existing capability
catalog, metrics, dimensions, analysis types, exact dates, rank method, window,
limit, sort and searchable filter values. It adds panels to the same result canvas;
it is not another independent Auto/Custom workspace.

The last successful panel remains visible during updates and failures. Revision
counters and AbortController reject late responses. Matching result scopes reuse
data for presentation changes. Each failed panel can be retried independently.
The summary is optional; every successful panel already contains factual insights.
The layout uses existing Light/Dark/AI tokens, shared charts and reduced-motion-aware
KPI animation. AI Chat and insurance continue through their existing paths.

## Architecture and security

- `app/schemas/analytics_workspace.py`: strict question, panel, plan, result, saved
  workspace and signed-evidence contracts; nested limits reject unsupported fields.
- `app/services/analytics/workspace.py`: ordinary bounded services, no agents.
- `/analytics/workspace/plan`: authenticated automotive scope -> conservative local
  interpretation or existing LLM completion -> strict parsing -> catalog and scope
  validation -> at most one correction -> clarification or validated business plan.
  Named business periods are checked server-side, including elapsed-week comparisons.
- `/analytics/workspace/run`: revalidates every supplied spec and permission scope,
  checks actual filter values, then calls the existing compiler/read-only runner.
  Daily execution is explicit and automotive-only. Database calls and elapsed time
  are metered, including filter checks. Nonadditive grouped values are never summed
  into a headline. Current-day completeness is explicitly qualified.
- `/analytics/workspace/narration`: accepts HMAC-signed compact factual statements
  generated by the run service, bound to user, role, region scope, semantic revision
  and ten-minute expiry. The LLM selects up to three evidence statements; final
  wording comes from governed facts. Client-modified facts cannot be narrated.
  This works across workers with the same signing key and semantic deployment;
  it does not rely on a worker-local result cache. No raw result sets go to the LLM.
- `/analytics/workspaces` and `/analytics/workspaces/{id}`: ownership-scoped save,
  list and reopen. Conditional revision updates prevent overwriting concurrent
  changes. Scope changes deny reopen; semantic changes trigger revalidation and a
  visible warning. Warehouse results are recomputed, never persisted as authority.

Common questions and compatible presentation/table edits have deterministic fast
paths. The reviewed question patterns and prompt examples are curated application
code, not automatic learning from arbitrary user SQL. Valid LLM plans have a bounded
128-entry, ten-minute cache keyed by identity, role, access scope, semantic revision,
business date, question and prior context; hits are revalidated. In-browser scoped
result reuse avoids SQL for compatible edits. Explicit retries fetch current data;
there is no new cross-request warehouse result cache or stale-data TTL assumption.

## Saving and compatibility

Migration `0013_analytics_workspaces` adds only the application-state workspace
table. It stores semantic plans, revision, permission scope, semantic revision and
up to fifty conversation turns. It does not change insurance or existing saved data.
Existing single analyses and owner-scoped AskWiz boards are available in Open saved
and imported into the unified canvas with fixed dates retained. Saving that imported
content creates a new workspace without modifying its original. Legacy Auto routes
remain for import/rollback and require their existing AskWiz API flag to be enabled.
The old UI appears only when the new frontend rollout flag is disabled.

## Activation and rollback

After restoring database connectivity, follow the normal deployment process:

1. From `apps/api`, use the project environment and run `python -m alembic upgrade head`.
   Confirm the application migration revision is `0013_analytics_workspaces`.
2. Set `ASK_ME_ANALYTICS_WORKSPACE_ENABLED=true` for the API.
3. Set `NEXT_PUBLIC_ASK_ME_ANALYTICS_WORKSPACE_ENABLED=true` and rebuild/restart web.
4. Perform live authenticated acceptance with automotive data and a configured LLM.

Both flags default false. Roll back by disabling both and rebuilding/restarting web;
keep the additive table so saved workspaces remain recoverable. Migration downgrade
drops only the new table and therefore loses newly saved workspaces: export/backup
them before any downgrade. No downgrade was run during development.

Known functional boundary: curated offline phrasing is intentionally conservative;
novel compound requests and semantic refinements require the configured LLM. The
application does not implement autonomous investigation, causal inference, writeback,
external actions, personal boards, scheduling or automatic training.
