INDEPENDENT CHECKS AND GENERAL FIXES
1. Amount change versus percentage change.
   Previously the typed ranking request could not express the basis, and comparison
   rankings silently selected percentage change. A reference fixture deliberately
   makes the largest rupee decline and largest percentage decline different models.
   It exposed the problem even though the prior SQL executed successfully.
   RequestedRanking now represents value/absolute_change/percent_change explicitly.
   Automotive YAML owns the unspecified comparison-ranking default: absolute_change.
   The interpretation prompt advertises the field and applied defaults are disclosed.
   This applies across measures/entities; there is no car-name/question patch.

2. Excluded measures versus requested outputs.
   The independent coverage veto treated an explicitly excluded measure as a required
   output. Exclusion operators are now recognized before applying the omission veto.
   Approved business-glossary aliases are included consistently alongside semantic
   aliases. Coverage also applies to supported analytical parts of mixed requests.
   This is still a conservative check, not a complete English negation parser.
   Complex conjunctions/exclusions need live holdout evaluation; no perfection claim.

3. Document-first mixed requests.
   A document-primary decision with an additional supported analytical intent could
   return only the document-unavailable message. It now retains the supported data
   handoff (or report handoff where appropriate), while documents remain gated and
   compliance remains explicitly unverified. No retrieval/vector dependency was added.

4. Deterministic regression configuration.
   The first full run found three document-test failures. Two stale tests expected
   retrieval even with document mode off; the third inherited RAG mode from local
   .env while intending to test legacy search. Tests now select the intended mode
   explicitly and assert that document-off/authorized-retrieval restrictions cannot
   be bypassed. Production knowledge/RAG code and permissions were not weakened.
   Added a positive rejection test for attempts to use legacy search with RAG enabled.

DELIVERED ACCEPTANCE TOOLS
scripts/chat_acceptance.py
  Uses the real authenticated Chat HTTP workflow, including follow-up conversations.
  Password is prompted without echo; no password argument/default/shared credential.
  TLS is required remotely; only loopback HTTP is allowed and redirects are disabled.
  Capture stores response IDs, hashes, status, model and usage, not raw questions,
  answers, result rows, SQL, cookies or credentials. Outputs should still remain private.
  Route/result/narration checks are separate. Exact text checks do not replace semantic
  human review; report panels always require review in Builder. Incomplete gold cannot
  become a complete pass. The comparison checks case/gold/dataset/user/scope/model
  compatibility and treats missing usage as unknown. No automatic rollout approval.

apps/api/tests/test_chat_postgres_acceptance.py
  Opt-in native PostgreSQL math smoke tests, independent of application/warehouse DSNs.
  Require an empty, disposable, test-named database and explicit setup permission.
  Refuse populated databases/existing Automotive schema; test setup rolls back.
  These were NOT executed here against PostgreSQL.

docs/chat-acceptance-candidates.json
  24 human-readable candidate questions, including grouped follow-ups, exclusions,
  amount/percentage declines, mixed evidence, trust, reports and regional scope.
  These are NOT genuinely blind holdouts: the implementer has seen them. A reviewer
  must author/select additional unseen questions privately before the live run.
  Neither the cases nor their reference SQL are included in runtime interpretation.
