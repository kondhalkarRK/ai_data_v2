AskDB leadership briefing (code-backed)

Executive summary

**AskDB (NQL Insight)** is a **POC-to-staging** natural-language analytics platform: **Next.js + FastAPI** over **PostgreSQL** warehouses, with a **governed semantic layer** (YAML packs), **read-only SQL execution**, optional **LLM-generated SQL**, regional **application-layer row scoping**, and **admin governance** (LLM settings, quotas, audit). **Numbers always come from SQL executed in your DB**; the LLM receives the **user question plus compact schema/glossary hints**, not bulk fact-table exports.

**Production readiness:** Strong **foundation** (auth, read-only analytics pools, SQL guardrails, EXPLAIN validation, usage quotas, log redaction, production config gates). **Not production-complete** without closing **regional scope gaps on some routes**, **enterprise IdP/RBAC**, **formal security testing**, **multi-DB connectors**, and **LLM data-processing agreements** (provider, residency, retention).

**Value proposition:** **Semantic-governed NLQ** that can sit **on top of existing Postgres (or future warehouses)** with **explicit SQL transparency**, **hybrid schema/LLM routing**, and **stewardship surfaces** (Semantic Atlas, Ontology Browser, Entity Catalog, DQ/Trust)—complementary to **Databricks/Snowflake/Power BI Copilot**, which optimize inside their own stacks.

1. Data security & LLM privacy

Q1. What data is sent to the LLM?

**Answer:** The **natural-language question**, a **system prompt** (PostgreSQL SELECT-only rules), and **domain hints** from `build_domain_sql_hints()`—tables/columns/measures, glossary rules, resolved filters, join hints—not full query result sets. Prior SQL snippets (≤\~1800 chars) and validator feedback may be included on retries. **Implemented:** `apps/api/app/services/llm.py` (`_slim_system_prompt`), `apps/api/app/services/chat/semantic_context.py`.

Q2. Are actual business records sent to the LLM?

**Answer:** **Not as the primary NLQ path.** Answers are produced by **executing SQL** against the analytics DB. **Partial exception:** **Knowledge/RAG** retrieves document chunks (citations to the user); hybrid chat may attach **top-k chunks** (`service.py` \~1187–1194). **DQ/reliability** can sample **up to 5 rows** internally (`reliability/engine.py`)—not the main chat LLM prompt.

Q3. How are API keys and credentials protected?

**Answer:** **Pydantic `SecretStr`** in settings; keys resolved server-side only (`config.py`, `governance/llm_config.py` `endpoint()`). **Log redaction** for DSNs, bearer tokens, JWTs (`observability/redaction.py`). Diagnostics expose **configured flags**, not secret values (`system.py` comment). **Implemented.**

Q4. What SQL security controls exist?

**Answer:** **`sql_is_safe()`**—SELECT/WITH only, blocks DML/chaining/dangerous PG functions (`analytics/sql_guardrails.py`). **DB layer:** analytics pool `default_transaction_read_only=on`, `statement_timeout`, `SET TRANSACTION READ ONLY` per connection (`db/session.py`). Chat uses **EXPLAIN** before run (`chat/service.py`). Row caps: `sql_max_result_rows`, NLQ default limit (`config.py`).

Q5. Is there dynamic data masking?

**Answer:** **No field-level masking layer** in code for LLM or API responses. Protection is **access control + scoped SQL + read-only role**. **Gap** for PII columns if mis-scoped SQL is generated.

Q6. Can users exfiltrate data via the LLM provider?

**Answer:** **Risk:** Question text and **schema metadata** (and filter values from question understanding) go to the configured provider (default OpenAI-compatible endpoint in `config.py`; admin can switch via `llm_catalog`). **Mitigation:** Use **private endpoint / Azure / Ollama** (`llm_config`, env keys); **weekly quotas** (`governance/quota.py`); **no bulk row upload** in NLQ path. **Partial**—no DLP scan on outbound prompts.

Q7. What about prompt injection?

**Answer:** **Regex-based** `is_out_of_bounds()` blocks obvious injection/SQL-in-question patterns (`chat/intents.py`); chat calls it (`service.py` \~480). **Partial**—not a dedicated LLM firewall; checklist marks corpus tests **pending** (`docs/06-security-checklist.md`).

Q8. Where do query results go?

**Answer:** To the **authenticated user** via SSE/API; stored in **query history** (app DB) with user scoping for non-admins (`chat/service.py`, `chat.py` history). **Not** re-sent to LLM for narrative except repair/validation flows with **SQL text**, not full result grids.

2. Governance & access control

Q9. How does authentication work?

**Answer:** **Email/password, Argon2id**, **JWT access + rotating refresh**, **CSRF** on state-changing cookie flows, **login rate limit** (`auth/service.py`, `deps.py`, `config.py`). **Implemented.**

Q10. What RBAC exists today?

**Answer:** Two roles: **`admin`** and **`user`** (`models/enums.py`). Admins see all query history in industry; users see own (`chat/service.py`). **Regional access** is a **separate dimension** (`user_region_access`, zones N/S/E/W)—not a third role. README “three roles” is **out of date** vs code.

Q11. How is regional data isolation enforced?

**Answer:** **SQL rewrite** on scoped analytics connections (`security/region_scope.py`, `RegionScopedConnection` via `get_scoped_analytics` in `deps.py`). Applied on **chat, KPI, executive, analytics, data preview, trust** routes (grep on routes). **Not PostgreSQL RLS.** Denials audited (`AdminAction.REGION_ACCESS_DENIED`).

Q12. Gaps in regional enforcement?

**Answer:** **Entity Catalog** refresh/lookup uses **unscoped** `analytics_connection` (`catalog/service.py`). **Ontology/semantic** APIs are metadata-first. **`dim_targets`** and some tables are **outside** `_SCOPED_TABLES` (`region_scope.py` \~155–169). **Gap** for strict multi-region production.

Q13. Audit logging?

**Answer:** **Login/logout/failures**, **admin LLM/DQ/catalog/graph changes**, **region denials** (`governance/audit.py`). **LLM usage** per question in `llm_usage` (`governance/usage.py`).

Q14. Usage quotas?

**Answer:** **Weekly token/call limits** per role from `weekly_limits`, enforced before chat (`quota.py`, `chat.py` `enforce_quota`). **Implemented.**

Q15. Database permissions model?

**Answer:** Runtime DSN uses **`askdb_reader`**; migrations/seeds use **`askdb_owner`** (`config.py`). API never needs DDL on warehouses. **Operator rule** in security checklist.

Q16. SQL injection prevention?

**Answer:** **Parameterized app DB**; analytics path relies on **LLM/governed SQL + `sql_is_safe` + EXPLAIN**—not a full SQL parser allowlist. **Defense in depth:** read-only DB user. **Residual risk** on creative SELECTs (e.g., subqueries touching unscoped tables).

Q17. AUTH_BYPASS in dev?

**Answer:** **`auth_bypass`** skips JWT and acts as first admin (`deps.py`); **refused in production** (`config.py` `_enforce_production_hardening`). Must stay **false** in prod.

3. Implementation & go-live plan

Q18. What is implemented?

**Answer:** Phases 1–7 **largely scaffolded** per `README.md` and `docs/03-phased-plan.md`: auth, semantic packs, ontology browser, 1M-row PG seeds (automotive/insurance), executive KPIs, SSE chat (schema / LLM / hybrid / knowledge routes), data preview/DQ, trust, admin center, regional RBAC on core analytics paths, unit tests e.g. `tests/unit/test_region_rls.py`.

Q19. What is missing for production?

**Answer:** From `docs/06-security-checklist.md`: **prompt-injection test corpus**, **a11y audit**, **SSRF-safe web fetch** (web retrieval gated off). **Multi-DB**, **enterprise SSO**, **PG RLS or policy engine**, **catalog scoped to region**, **production Qdrant/Mongo** (RAG often **hash embed** locally). README: live verification depends on **local Postgres + optional LLM key**.

4. Database support

Q21. What is supported today?

**Answer:** **PostgreSQL only**—app DB `askdb_app` + per-industry analytics URLs (`config.py`, `Industry` enum: **automotive**, **insurance**). Async driver: **`postgresql+psycopg`**.

Q22. What would SQL Server / Snowflake / Databricks SQL / BigQuery take?

**Answer:** **Not in repo** (no connectors). Would need: (1) **dialect-specific** semantic packs and `sql_is_safe`/identifier rules; (2) **connection registry** like `DatabaseRegistry`; (3) **region scoping** rewritten for each dialect or **delegated to warehouse RLS**; (4) **EXPLAIN** equivalents; (5) **read-only roles** and timeouts per platform. Estimate: **connector + compiler slice per engine**, not a config toggle.

5. Competitive positioning

Q23. vs Databricks / Snowflake AI?

**Answer:** They offer **in-warehouse** genie/copilot tied to **their** compute and governance. AskDB is **application-layer NLQ** with **visible SQL**, **semantic YAML stewardship**, and **portable Postgres-first** deployment—**complement** when the warehouse is PG or when you want a **consistent UX** across industries/packs.

Q24. vs Power BI Copilot?

**Answer:** Copilot optimizes **reports/datasets in Power BI**. AskDB targets **ad hoc governed SQL** and **operational semantic layer** (catalog, DQ, trust, ontology exploration) with **API-first** integration. **Different buyer moment:** embedded analytics vs analyst desktop.

Q25. Realistic differentiators?

**Answer:** **Hybrid governance** (`ExecutionMode`: SCHEMA / LLM / HYBRID in `enums.py`); **admin-governed LLM** (`llm_config.py`); **transparent SQL + EXPLAIN**; **industry semantic packs**; **Ontology Browser** for stewards (explicitly **not** in LLM path today—`docs/ontology-browser-and-llm.md`). **Weak differentiator** if the customer is already all-in on one vendor’s copilot and RLS.

Q26. Compete or complement?

**Answer:** **Complement by default**—front-end to **Postgres or future warehouses** and **Capgemini-style** delivery (semantic modeling, DQ, regional demos). **Compete** only where buyers want a **standalone governed NLQ product** without replacing the warehouse.

Top 5 security risks & actions before go-live

| **#** | **Risk**                                                          | **Evidence**                                                           | **Recommended action**                                                                           |
| :---- | :---------------------------------------------------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------- |
| 1     | **LLM prompt leakage** (questions + schema hints to external API) | `llm.py`, `semantic_context.py`, default `llm_base_url` in `config.py` | Private LLM/Azure; DPA; optional on-prem Ollama; prompt logging policy                           |
| 2     | **Incomplete regional scope** (catalog, unlisted tables)          | `catalog/service.py` unscoped analytics; `_SCOPED_TABLES` finite list  | Scope catalog reads; extend table map; or **warehouse RLS**                                      |
| 3     | **LLM-generated SQL** bypassing intent                            | Regex guardrails only; not full SQL AST                                | Expand tests; governed-first mode (`nlq_llm_reasoning_mode`); block unscoped tables in validator |
| 4     | **Weak prompt-injection defense**                                 | `intents.py`; checklist **pending**                                    | Security test corpus; rate limits; refuse system override patterns                               |
| 5     | **Dev auth bypass / misconfig**                                   | `auth_bypass`, short JWT in prod blocked but ops error-prone           | CI guard; separate prod env templates; no bypass in staging                                      |

**Bottom line for leadership:** AskDB is a **credible governed NLQ POC** with **real controls** on the main query path, but **go-live** should be framed as **pilot with explicit LLM and regional-scope policies**, not as a drop-in replacement for warehouse-native copilots until **IdP, scope completeness, security testing, and target DB strategy** are decided
