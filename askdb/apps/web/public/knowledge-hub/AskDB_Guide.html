One place to understand Ask DB

This hub is for developers, architects, business users, and stakeholders. It explains what each workspace does, how a question becomes a governed number, and how the hosted stack (Vercel UI, Render API, Supabase Postgres, optional Mongo/Qdrant, Capgemini-compatible LLM) fits together.

Overall solution architecture

The browser never holds an LLM key and never executes SQL. Vercel serves Next.js. FastAPI on Render owns auth, NLQ, KPIs, and guardrails. Postgres (hosted as one Supabase project with schemas, or three local DBs) stores app state and analytics facts.

LLM interaction & reasoning

The model proposes SQL and optional narrative. It does not compute KPIs in Python. Timeouts, retries, and a circuit breaker protect the API. Home “LLM connected” only means a key is configured.

flowchart TD
  Q[User question] --> U[Question understanding]
  U --> H[YAML hints + glossary ALWAYS/NEVER]
  H --> P[System prompt: one PostgreSQL SELECT]
  P --> C{Circuit open?}
  C -->|yes| F[Degraded message]
  C -->|no| L[complete_chat]
  L --> V[sql_is_safe + pack allowlist]
  V -->|fail| R[Auto-repair or failure card]
  V -->|pass| X[Execute]

Security & access control

  • HttpOnly cookies nql_access / nql_refresh + CSRF double-submit.
  • Roles: viewer, analyst, admin. Chat and Builder require analyst+.
  • Analytics pools: SET TRANSACTION READ ONLY, statement timeout, max rows.
  • Production: AUTH_BYPASS=false, COOKIE_SECURE=true.

Module playbooks

Each module below expands. Search above filters these cards.

Analytics Builder

Purpose. No-code analysis over the semantic layer without writing SQL.

Key features. Metrics, dimensions, filters, analysis kinds (trend, ranking, contribution), save/share, chart/table/heatmap previews.

User workflow. Pick industry → choose measures & dims → optional filters → Run → inspect chart/SQL → save.

Technical workflow. UI builds AnalyticsSpec → POST /api/v1/analytics/run → runner compiles guarded SQL → rows + viz hint.

Input
Spec JSON, industry header, session cookie.
Output
Columns, rows, title, recommended viz.

Depends on. Semantic pack, read-only analytics DB, ResultChart.

Data Preview

Purpose. Browse governed tables for the active industry.

Key features. Table list from the pack, keyset pagination, no full-table download.

User workflow. Open Data Preview → select table → page through rows.

Technical workflow. GET /api/v1/data/tables then preview with LIMIT/keyset.

I/O. Table name in; page of rows out. Depends on pack physical names + reader role.

Executive Intelligence Dashboard

Purpose. Domain KPIs, grounded insights, and performance series for leadership.

Key features. Industry-aware KPI grid, AI insight votes, filters (region/make/window), heatmap/explorer.

User workflow. Home or Executive → switch industry → read cards → drill via explorer.

Technical workflow. KPI SQL engines (automotive/insurance) + executive routes; numbers always from SQL.

Depends on. KPI service, trust flags, Progressive Explorer, charts.

Progressive Drill-Down Explorer

Purpose. Guided Region → Dealer → Brand → Model story for automotive (insurance uses analogous cuts).

User workflow. Click a region → dealers → models; filters sync with the dashboard bar.

Technical workflow. /executive/region-map, dealers, models endpoints; metric units vs revenue.

ASK DB / Natural Language Query

Purpose. Ask governed questions in English; get SQL-backed answers plus narrative.

Key features. Question understanding, template hits, LLM SQL, citations, follow-ups, cancel, saved prompts.

User workflow. AI Chat → type question → review table/SQL/trust → follow-up.

Technical workflow. Hosted UI uses POST /api/v1/chat/ask-sync (JSON) because Vercel buffers SSE. Locally SSE /chat/ask still exists.

I/O. Question + industry in; events (sql, rows, meta, tokens, failure) out.

Depends on. LLM key on API, YAML pack, analytics DB, optional knowledge store.

Semantic Layer

Purpose. Single source of entities, measures, joins, and rules.

Technical workflow. Load apps/api/semantic/packs/{industry}/*.yaml at runtime. Docker image must copy the semantic/ folder.

Output. Pack API, ontology snapshot, NLQ hints. Never inferred from scanning tables ad hoc.

Ontology Explorer

Purpose. Visual knowledge graph: network, centrality, hierarchy, lineage, constellation.

User workflow. Ontology Browser → choose layout → inspect node → business vs technical overlay.

Technical workflow. Snapshot compiled from YAML only; node clicks do not query Postgres.

Knowledge Base

Purpose. Upload reports so Chat can cite narrative context.

User workflow. Knowledge Hub → upload → wait for index → ask in Chat.

Technical workflow. Filesystem store under data/knowledge (temp fallback on Render); optional Mongo/Qdrant mirrors.

Data Trust Center

Purpose. Observability for freshness, incidents, and trust score.

Depends on. Semantic pack (missing pack.yaml fails this page) + DQ services.

Business Glossary

Purpose. Human definitions and ALWAYS/NEVER disambiguation (e.g. dealer vs salesman).

Lives in. business_glossary.yaml inside each industry pack. Consumed by NLQ and Semantic Atlas.

Industry Packs

Purpose. Swap the entire semantic + KPI surface with one industry flag.

Packs. Automotive (sales, dealers, models) and Insurance (claims, policies, loss ratio).

Switch. Session default + per-tab override via x-industry.

Saved Questions

Purpose. Pin NLQ or Builder questions for reuse.

Store. askdb_app tables. Open from Chat deep link ?q=.

SQL Explorer

Purpose. Show the exact SELECT that produced an answer (Chat / Builder / history).

Governance. Display only; users cannot submit arbitrary SQL from the UI.

Chart & Visualization Engine

Purpose. Turn row sets into bar/line/area/pie/scatter/KPI/heatmap/treemap.

Component. ResultChart plus Builder previews. Labels come from semantic titles, not raw column ids where possible.

Data Quality Monitoring

Purpose. Score completeness/freshness and surface incidents on Trust Center and KPI caution states.

Governance & Lineage

Purpose. Show how a measure traces to physical tables/columns via YAML lineage, not inferred FK scans.

UI. Ontology lineage layout + technical overlay (physical names).

User Management & Security

Purpose. Identity, roles, audit of login, and admin-only logs.

Workflow. create_admin.py seeds the first admin; admins create users via API.

Hosted. Real login, no AUTH_BYPASS. System Logs under Admin.
