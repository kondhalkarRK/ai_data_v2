One place to understand Ask DB

This hub is for developers, architects, business users, and stakeholders. It explains what each workspace does, how a question in AI Chat becomes a governed number, how every question is recorded in history, and how the hosted stack (Vercel UI, Render API, Supabase Postgres, optional Mongo/Qdrant, Capgemini-compatible LLM) fits together.

What's new in this release

Understands business words first

Brands, cities, models and body types are matched to real data values before any SQL is written ("suzuki" → Maruti Suzuki, "Bangalore" → Bengaluru, "Hundai" → Hyundai).

Structured plan

Every question becomes a plan of intent, brand, metric, dimension, filters, analysis and chart. The answer card shows it as "Understood as".

Smarter SQL

Multi-brand IN filters, market share with window functions, year and month grains, and a 24-month default window for open-ended trends.

Clarify, don't fail

Vague, unknown or unsupported questions get a friendly clarification with clickable suggestions instead of a "SQL execution failed" error.

Follow-ups

"What about Hyundai?" or "Only in Mumbai" reuse the last answer's metric, grain and filters from question history.

Question history

Every question is stored with status, SQL, trust score, latency and plan state, and is visible on the Query History page.

Multi-series charts

Grouped bars and multi-line charts with a legend when a result has several numeric columns (revenue and units).

Ontology Map

A fourth Knowledge Graph view with business domains, community boundaries, centrality, hierarchy, search and cross-domain links.

Chat vocabulary kept separate

Chat-only rules live in chat_vocabulary.yaml, so tuning chat never changes the Knowledge Graph.

Overall solution architecture

The browser never holds an LLM key and never executes SQL. Vercel serves Next.js. FastAPI on Render owns auth, AI Chat, KPIs and guardrails. Postgres (one Supabase project with schemas when hosted, three local databases in development) stores app state, question history and analytics facts.

A real run of "Compare MG sales by year in Mumbai" through the automotive pack. Every output below is what the planner actually produced.

    City lives in the region dimension and make in the carline dimension, so both joins are added.

    fact_sales → dim_region · fact_sales → dim_carline

    "Sales" means revenue in the glossary; units are returned alongside for the second series.

    revenue = SUM(total_sales) · units_sold = SUM(order_qty)

    SQL Generation semantic compiler, no LLM needed

    SELECT EXTRACT(YEAR FROM f.sales_date)::int AS year,
       SUM(f.total_sales) AS revenue,
       SUM(f.order_qty)   AS units_sold
FROM automotive.fact_sales f
JOIN automotive.dim_region  r ON r.region_id  = f.region_id
JOIN automotive.dim_carline c ON c.carline_id = f.carline_id
WHERE r.city = 'Mumbai' AND c.make = 'MG'
GROUP BY 1 ORDER BY 1 LIMIT 100

    SQL Validation

    SELECT-only, tables in the automotive allowlist, both filters and the year grain present, LIMIT set.

    valid

    EXPLAIN succeeds, so no repair is needed. If a column were wrong, the pack would supply the correct one and validation would run again.

    skipped (EXPLAIN ok)

    Runs in a read-only transaction with a statement timeout.

    one row per year: year, revenue, units_sold

    A time grain gets a line chart; two numeric columns enable the multi-series option.

    line chart · series = revenue, units_sold

Follow-up questions

After a successful answer the plan is saved as queryState in the history row. The next question in the same conversation reads the latest completed row and merges it, so short follow-ups work.

Turn 1 · "MG sales by year"
  1. User → ChatServiceMG sales by year
  2. ChatService → PlannerPlan from scratch
  3. Planner → ChatServicerevenue by year, make = MG
  4. ChatService → Historycompleted, queryState saved
Turn 2 · "What about Hyundai?"
  1. ChatService → HistoryLatest completed row in this conversation
  2. History → ChatServicequeryState: revenue, year, make = MG
  3. ChatService → PlannerNew brand Hyundai + prior state
  4. Planner → ChatServicerevenue by year, make = Hyundai
Or turn 2 · "Only in Mumbai"
  1. ChatService → PlannerAdd city = Mumbai to prior state
  2. Planner → ChatServicerevenue by year, make = MG, city = Mumbai

Market share SQL (real output)

WITH base AS (
  SELECT EXTRACT(YEAR FROM f.sales_date)::int AS year, c.make AS make,
         SUM(f.order_qty) AS units_sold, SUM(f.total_sales) AS revenue
  FROM automotive.fact_sales f
  JOIN automotive.dim_carline c ON c.carline_id = f.carline_id
  GROUP BY 1, 2
), shared AS (
  SELECT base.*, 100.0 * units_sold / NULLIF(SUM(units_sold) OVER (PARTITION BY year), 0) AS market_share_pct
  FROM base
)
SELECT year, make, market_share_pct, units_sold, revenue
FROM shared WHERE make IN ('Maruti Suzuki')
ORDER BY year, market_share_pct DESC LIMIT 100

Share is computed over all brands first and filtered afterwards; filtering first would always give 100%.

LLM interaction & reasoning

Most questions are compiled from the semantic model without the LLM. The model is only a fallback that writes SQL when the planner cannot; narration is built from the plan and results in Python, and the model never computes KPIs. Module playbooks

Each module below expands. Search above filters these cards.

Analytics Builder

Purpose. No-code analysis over the semantic layer without writing SQL.

Key features. Metrics, dimensions, filters, analysis kinds (trend, ranking, contribution), save/share, chart/table/heatmap previews.

User workflow. Pick industry → choose measures & dims → optional filters → Run → inspect chart/SQL → save.

Technical workflow. UI builds AnalyticsSpec → POST /api/v1/analytics/run → runner compiles guarded SQL → rows + viz hint.

Input
Spec JSON, industry header, session cookie.
Output
Columns, rows, title, recommended viz.

Depends on. Semantic pack, read-only analytics DB, ResultChart.

Data Preview

Purpose. Browse governed tables for the active industry.

Key features. Table list from the pack, keyset pagination, no full-table download.

User workflow. Open Data Preview → select table → page through rows.

Technical workflow. GET /api/v1/data/tables then preview with LIMIT/keyset.

I/O. Table name in; page of rows out. Depends on pack physical names + reader role.

Executive Intelligence Dashboard

Purpose. Domain KPIs, grounded insights, and performance series for leadership.

Key features. Industry-aware KPI grid, AI insight votes, filters (region/make/window), heatmap/explorer.

User workflow. Home or Executive → switch industry → read cards → drill via explorer.

Technical workflow. KPI SQL engines (automotive/insurance) + executive routes; numbers always from SQL.

Depends on. KPI service, trust flags, Progressive Explorer, charts.

Progressive Drill-Down Explorer

Purpose. Guided Region → Dealer → Brand → Model story for automotive (insurance uses analogous cuts).

User workflow. Click a region → dealers → models; filters sync with the dashboard bar.

Technical workflow. /executive/region-map, dealers, models endpoints; metric units vs revenue.

ASK DB / AI Chat

Purpose. Ask governed questions in plain English and get SQL-backed answers, charts and a narrative.

Key features. Entity resolution (exact, synonym, fuzzy, alias, glossary), structured plan shown as "Understood as", multi-brand comparisons, market share, 24-month default trend window, clarification and recovery cards with clickable suggestions, follow-ups, multi-series charts, cancel, saved prompts, citations.

User workflow. AI Chat → type a question → check "Understood as" → review chart, table, SQL and trust → click a suggestion or ask a follow-up.

Technical workflow. Hosted UI uses POST /api/v1/chat/ask-sync (JSON) because Vercel buffers SSE; locally the SSE /chat/ask endpoint is used. See the 14 phases.

I/O. Question, industry and conversationId in; events (stage, plan, sql, columns, rows, chart, clarification, tokens, followups, done) out.

Depends on. YAML pack and chat vocabulary, value dictionary, analytics DB, query history, LLM key on the API (SQL fallback only), optional knowledge store.

Query History New

Purpose. An audit trail of every chat question, and the memory used for follow-ups.

Key features. Question, status (running, completed, failed, cancelled), trust score, latency, date and the SQL that ran.

User workflow. Open Query History → scan recent questions → expand a row to see its SQL.

Technical workflow. GET /api/v1/history returns the last 50 rows for the user and industry from query_history. See Question history.

Depends on. App database (askdb_app), chat service writing each row.

Semantic Layer

Purpose. Single source of entities, measures, joins, value domains and rules.

Files. pack.yaml, semantic_model.yaml, business_glossary.yaml and the chat-only chat_vocabulary.yaml under apps/api/semantic/packs/{industry}/. The Docker image must copy the semantic/ folder.

Output. Pack API, ontology snapshot, chat resolver vocabulary and planner formulas. Never inferred from scanning tables ad hoc.

Knowledge Graph / Ontology Explorer

Purpose. A visual map of business concepts and how they relate.

Views. Knowledge Graph (recommended), Relationship Network, Simple Relationship View, and the new Ontology Map with domain clusters, Force / Centrality / Hierarchy layouts, domain pills, search and cross-domain links.

User workflow. Semantic Atlas → pick a view → click a concept → switch between business and technical names.

Technical workflow. Snapshot compiled from YAML (plus glossary terms for the Ontology Map); node clicks never query Postgres.

Knowledge Base

Purpose. Upload reports so Chat can cite narrative context.

User workflow. Knowledge Hub → upload → wait for index → ask in Chat.

Technical workflow. Filesystem store under data/knowledge (temp fallback on Render); optional Mongo/Qdrant mirrors.

Data Trust Center

Purpose. Observability for freshness, incidents, and trust score.

Depends on. Semantic pack (missing pack.yaml fails this page) + DQ services.

Business Glossary

Purpose. Human definitions, synonyms and ALWAYS/NEVER disambiguation (e.g. dealer vs salesman, "sales" means revenue).

Lives in. business_glossary.yaml inside each industry pack. Used by the chat resolver (glossary matches), the planner, Semantic Atlas and the Ontology Map.

Industry Packs

Purpose. Swap the entire semantic + KPI surface with one industry flag.

Packs. Automotive (sales, dealers, models) and Insurance (claims, policies, loss ratio).

Switch. Session default + per-tab override via x-industry. Question history is filtered by industry too.

Saved Questions

Purpose. Pin chat or Builder questions for reuse.

Store. askdb_app tables (GET/POST /api/v1/questions). Open from Chat deep link ?q=.

SQL Explorer

Purpose. Show the exact SELECT that produced an answer (Chat / Builder / Query History).

Governance. Display only; users cannot submit arbitrary SQL from the UI.

Chart & Visualization Engine

Purpose. Turn row sets into bar / line / area / pie / scatter / KPI / heatmap / treemap.

Component. ResultChart plus Builder previews. When a result has several numeric columns, "All series" draws grouped bars or multiple lines with a legend. Labels come from semantic titles, not raw column ids where possible.

Data Quality Monitoring

Purpose. Score completeness/freshness and surface incidents on Trust Center and KPI caution states.

Governance & Lineage

Purpose. Show how a measure traces to physical tables/columns via YAML lineage, not inferred FK scans.

UI. Knowledge Graph lineage + technical overlay (physical names). Chat answers link back to their SQL in Query History.

User Management & Security

Purpose. Identity, roles, audit of login, and admin-only logs.

Workflow. create_admin.py seeds the first admin; admins create users via API.

Hosted. Real login, no AUTH_BYPASS. System Logs under Admin.

How to open this hub

After a Vercel deploy: /knowledge-hub/AskDB_Guide.html on the same site. Locally: askdb/apps/web/public/knowledge-hub/AskDB_Guide.html, or http://localhost:3000/knowledge-hub/AskDB_Guide.html with the dev server running.
