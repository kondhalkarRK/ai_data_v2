How routing & conversation work now

This guide reflects the current backend path in ChatService.ask_stream, pre_plan.py, message_classifier.py, conversation_memory.py, and the eval harness (chat_routing_eval.yaml). It is not a generic ChatGPT clone: answers about your numbers always go through the semantic layer and SQL guardrails.

Is it like a ChatGPT conversation?

Similar to ChatGPT

  • One conversation keeps context across turns (same conversationId).
  • Short replies after a data answer: “What about South?”, “Break it down by month”.
  • Greetings, thanks, and light chitchat get a brief reply without running SQL.
  • General knowledge (e.g. capitals) can get a short LLM answer with a clear “not from your data” note.
  • Clarification when the system is unsure instead of inventing metrics or regions.

Not like ChatGPT

  • No free-form answers about your revenue, claims, or KPIs without validated SQL.
  • No live web (weather, crypto, sports scores).
  • No deleting data, other users’ history, or bypassing instructions.
  • Region-scoped users only see data their RBAC allows.
  • Memory for analytics expires (TTL and turn cap); unrelated questions do not silently reuse an old query.

Configuration (what is on in production by default)

SettingDefaultEffect
chat_router_enabled (default true) false Rule classifier runs in shadow only (logs route; does not change behavior). Set true to enable greetings, app help, document cues, etc. before planning.
chat_follow_up_guard_enabled true Short follow-ups must name a real value, metric, date, or operation—or the app asks for clarification instead of reusing SQL.
chat_question_rewrites_enabled true Strips leading “why did / explain / what drove” for planning; splits “Explain X and show …” into data + glossary definition.
chat_structured_classifier_enabled false Optional single LLM JSON call (intent + restated question) when deterministic planning would clarify; falls back to clarification on error.
chat_analytical_context_ttl_seconds 1800 (30 min) After this, contextual follow-ups prompt you to ask the full question again.
chat_analytical_context_max_turns 8 Maximum chained data follow-ups on one analytical context.

End-to-end routing pipeline

Every message in a conversation follows this order (see run_pre_plan + plan_turn):

1. Region guardForbidden zone names in text → access denied (RBAC).
→
2. Early classifierIf router on: greeting, thanks, unsafe, live external, app help, documents—no schema load.
3. Pack + valuesSemantic pack and value dictionary loaded for governed vocabulary.
→
4. General knowledgeIf router on: “What is …” with no data words → LLM (disclaimer), no SQL.
5. MemoryRefresh clears stale context; expiry blocks old follow-ups; scope revalidates filters.
→
6. Follow-up guardShort messages need anchor (South, by month, last year, top 5…).
7. plan_turnSpell check → entity resolve → intent → governed SQL template.
→
8. RewritesWhy/explain strip; compound “explain X and show …” → plan data half + definition event.
9. Optional LLMStructured classifier or legacy interpret_question only if plan would clarify.
→
10. ExecuteValidated SQL, narrative, charts—or clarification / recovery.

After a successful data answer, SessionMemory.analytical stores a validated plan (metric, dimensions, filters)—not free-text PII—for the next turn.

What kinds of questions are supported?

Eval labels in chat_routing_eval.yaml map to user-visible behavior:

DATA_QUERY Governed analytics (main path)

  • Metrics and dimensions from the semantic layer: revenue, units, premium, loss ratio, by region, month, dealer, product, etc.
  • Examples: “Revenue by region”, “Top 5 dealers in Mumbai by units”, “Loss ratio by month”.
  • Unresolved brands/regions → clarification options, not guessed SQL.

DATA_FOLLOW_UP Conversational drill-down

  • Requires active analytical memory and a valid anchor (see Follow-ups).
  • Examples: “What about South?”, “Break it down by month”, “Bottom 5 instead”, “Last year?”, “Add Delhi”, “Same for revenue”.
  • UI may show interpretation: e.g. “Showing revenue for South”.

GENERAL_CHAT Small talk (router on)

  • Hello, thanks, jokes, non-data chitchat (e.g. dinner)—brief LLM or template; no SQL.
  • After a failed or empty data turn, jokes are suppressed.

APP_HELP Product & semantic layer help

  • What tables/metrics/KPIs exist, what loss ratio means in this app, how to ask about premium vs earned premium.
  • Answers from pack + glossary only; missing terms are stated honestly.

GENERAL_KNOWLEDGE World facts (router on)

  • Opener like “Explain …” / “What is the capital of …” with no governed data vocabulary.
  • LLM with strict prompt: never imply a database check.

DOCUMENT_QUERY Uploaded documents

  • Phrases like summarize report, policy document, uploaded file → knowledge search if documents exist; otherwise a clear “no documents” message.

OUT_OF_SCOPE_LIVE External / live feeds

  • Weather, crypto, sports, elections, stock prices → polite refusal.

UNSUPPORTED Unsafe or out of policy

  • Delete/drop table, other users’ chat, prompt injection, regions outside semantic allow-list (is_out_of_bounds).

CLARIFICATION Need more detail

  • Ambiguous metric (“Show sales”), vague follow-up (“What about it?”), guard blocked, plan validation failed, or LLM classifier timeout.

Conversation memory (multi-turn)

Stored per user + conversation in conversations.session_memory (JSON):

Memory slicePurpose
Analytical context Last successful plan: metric, dimensions, filters, time grain, validated plan JSON. Powers follow-ups and RBAC revalidation.
Recent turns Short rolling transcript for UX (not used to invent SQL).
General chat turns Optional small-talk history when router handles greetings via LLM.
Pending clarification If you were asked “Revenue or units?”, your next short reply completes the original question.

Refresh phrases (e.g. “refresh”, “reload”, “update the numbers”) bypass query cache and start fresh analytical context. Unrelated long questions do not inherit the prior SQL plan unless they look like follow-ups.

Follow-up guard (when it runs SQL vs asks you)

With guard enabled, a short message reuses the prior plan only if it includes at least one of:

  • A known value (e.g. South, Mumbai, a claim status from the value dictionary).
  • A metric / dimension / glossary term from the industry semantic pack.
  • A date phrase (last year, Q3, by quarter, YTD, month names).
  • An operation: break down, top/bottom N, add/include, same for, compare, only X, instead.

“What about dinner?” after a data answer → GENERAL_CHAT (router) or clarification (guard), not SQL. Values valid only in another industry (e.g. insurance “Repudiated” in automotive) do not anchor a follow-up.

Example conversation threads

Thread A — Data drill-down (ChatGPT-style, governed)

  1. You: Revenue by region → DATA_QUERY, SQL + chart.
  2. You: What about South? → DATA_FOLLOW_UP, same metric, filter South.
  3. You: Break it down by month → DATA_FOLLOW_UP, adds time grain.
  4. You: Thanks → GENERAL_CHAT, no SQL.

Thread B — Help + data (router on)

  1. You: What metrics are available in Ask DB? → APP_HELP from semantic pack.
  2. You: Show me total revenue last month → DATA_QUERY.

Thread C — Clarification instead of guessing

  1. You: Show sales → CLARIFICATION (metric ambiguous).
  2. You: Revenue → pending clarification merged → DATA_QUERY.

Thread D — Why question with rewrite

  1. You: Why did revenue drop in the West region? → rewriter may plan revenue drop in the West region → DATA_QUERY if vocabulary resolves.

Limits & honesty

  • Router off (default): behavior matches legacy path for most analytics; shadow logs show what would have routed.
  • Compound questions with undefined terms (e.g. “Explain churn and show last quarter” when churn is not in the insurance glossary) may still clarify rather than invent a metric.
  • Streaming is token-by-token from completed LLM text for chat/knowledge paths; true token streaming from the provider is not wired everywhere.
  • Eval harness: 78/79 routing labels with router + guard + rewrites; full accuracy depends on enabling the same flags in production.
